How a mixture-of-experts transformer decides which weights to touch

A dense transformer applies the same feed-forward network to every token. A mixture-of-experts (MoE) transformer replaces that single network with many smaller networks, the experts, and adds a router in front of them. For each token, the router computes a score for every expert, keeps the top few, and sends the token only to those. Gemma 4 26B-A4B uses 128 experts per layer and activates 8 of them per token, in addition to a small dense network that every token passes through. The total parameter count is about 25 billion, but any single token only exercises about 3.8 billion of them.

This matters for memory traffic more than for arithmetic. Generating one token means reading, for every layer, the weights of the eight selected experts. At four bits per weight, one expert in one layer is about 3.3 megabytes, so a token touches roughly 800 megabytes of expert weights across the thirty layers if nothing is cached. A desktop with 60 gigabytes per second of memory bandwidth barely notices. A Raspberry Pi 5, whose memory subsystem delivers about ten gigabytes per second to a CPU program and whose storage delivers somewhere between ninety megabytes per second from a microSD card and nine hundred megabytes per second from an NVMe drive on a PCIe Gen 3 lane, notices a great deal.

The question that decides whether such a model is usable on a small board is therefore not how many operations it performs but how many bytes must cross the slowest link per token. If the eight experts chosen for the current token were also chosen for the previous token, their weights are already in RAM and nothing needs to be read from storage. If the router jumps to eight experts that have not been used in a while, each miss costs a multi-megabyte read. The hit rate of whatever cache sits between storage and the CPU is the number that matters.

Three properties of real routers help. First, expert popularity is skewed: a minority of experts receives a majority of the traffic, so a cache that keeps the popular ones warm serves most requests. Second, consecutive tokens share experts far more often than chance would predict, because neighbouring tokens tend to belong to the same syntactic and semantic neighbourhood. Third, routing is partly predictable from the routing decisions of earlier layers, which allows prefetching the next layer's experts while the current layer computes.

None of these properties can be assumed for a particular model. They have to be measured by recording which experts each layer selects for each token on a representative text, then replaying that record against a simulated cache of a given size with a given replacement policy. The replay yields a hit rate, the hit rate yields bytes per token, and bytes per token divided by storage bandwidth yields a lower bound on the time per token. If that bound is well below the time the CPU needs for the arithmetic, the storage link is not the bottleneck and the model is as fast as the CPU allows. If it is above, the storage link dominates and the only remedies are a faster drive, more RAM for the cache, a smarter replacement policy, or a smaller quantisation of the expert weights.

A dense model offers no such escape. Every token must read every weight. For a thirty-one billion parameter model at four bits that is about seventeen gigabytes per token, which takes about twenty seconds at nine hundred megabytes per second. The only known way to amortise that read is to verify several tokens in a single pass over the weights, which speculative decoding does when a small draft model proposes continuations that the large model then checks in a batch. The draft must live in RAM and be accepted often; a draft that is rejected most of the time wastes the pass.
