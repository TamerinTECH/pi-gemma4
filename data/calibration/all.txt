How a mixture-of-experts transformer decides which weights to touch

A dense transformer applies the same feed-forward network to every token. A mixture-of-experts (MoE) transformer replaces that single network with many smaller networks, the experts, and adds a router in front of them. For each token, the router computes a score for every expert, keeps the top few, and sends the token only to those. Gemma 4 26B-A4B uses 128 experts per layer and activates 8 of them per token, in addition to a small dense network that every token passes through. The total parameter count is about 25 billion, but any single token only exercises about 3.8 billion of them.

This matters for memory traffic more than for arithmetic. Generating one token means reading, for every layer, the weights of the eight selected experts. At four bits per weight, one expert in one layer is about 3.3 megabytes, so a token touches roughly 800 megabytes of expert weights across the thirty layers if nothing is cached. A desktop with 60 gigabytes per second of memory bandwidth barely notices. A Raspberry Pi 5, whose memory subsystem delivers about ten gigabytes per second to a CPU program and whose storage delivers somewhere between ninety megabytes per second from a microSD card and nine hundred megabytes per second from an NVMe drive on a PCIe Gen 3 lane, notices a great deal.

The question that decides whether such a model is usable on a small board is therefore not how many operations it performs but how many bytes must cross the slowest link per token. If the eight experts chosen for the current token were also chosen for the previous token, their weights are already in RAM and nothing needs to be read from storage. If the router jumps to eight experts that have not been used in a while, each miss costs a multi-megabyte read. The hit rate of whatever cache sits between storage and the CPU is the number that matters.

Three properties of real routers help. First, expert popularity is skewed: a minority of experts receives a majority of the traffic, so a cache that keeps the popular ones warm serves most requests. Second, consecutive tokens share experts far more often than chance would predict, because neighbouring tokens tend to belong to the same syntactic and semantic neighbourhood. Third, routing is partly predictable from the routing decisions of earlier layers, which allows prefetching the next layer's experts while the current layer computes.

None of these properties can be assumed for a particular model. They have to be measured by recording which experts each layer selects for each token on a representative text, then replaying that record against a simulated cache of a given size with a given replacement policy. The replay yields a hit rate, the hit rate yields bytes per token, and bytes per token divided by storage bandwidth yields a lower bound on the time per token. If that bound is well below the time the CPU needs for the arithmetic, the storage link is not the bottleneck and the model is as fast as the CPU allows. If it is above, the storage link dominates and the only remedies are a faster drive, more RAM for the cache, a smarter replacement policy, or a smaller quantisation of the expert weights.

The only known way to amortise that read is to verify several tokens in a single pass over the weights, which speculative decoding does when a small draft model proposes continuations that the large model then checks in a batch. The draft must live in RAM and be accepted often; a draft that is rejected most of the time wastes the pass.

"וידאו דחוס" של מחשבה: לחשב רק מה השתנה. במקום לחשב מחדש את כל המצב הפנימי בכל צעד, המודל ישמור מצב קודם ויעדכן רק את השינוי. בחלק ליניארי זה פשוט מתמטית: W(x+Δx) = Wx + WΔx. אם כבר חישבנו את Wx, אפשר לחשב רק את התיקון. אבל יש כאן מלכודת: אם השינוי גדול ומפוזר, לא חסכנו כמעט כלום. לכן הייתי מנסה לאמן מודל שבו השינויים הפנימיים הם בדרך כלל קטנים ומרוכזים. רוב הרכיבים לא משתנים; רק רכיבים שקיבלו מידע חדש מתעוררים. מדי פעם מבצעים רענון מלא כדי למנוע הצטברות שגיאות. הקושי העיקרי: תוספת קטנה בטקסט, למשל המילה "לא", יכולה לשנות לחלוטין את המשמעות. מנגנון כזה חייב לדעת מתי עדכון קטן מספיק ומתי צריך לחשב מחדש הרבה.

4. מוח איטי ופה מהיר. המודל הגדול מחליט מה לומר; מודל קטן אחראי להגיד את זה. הייתי בונה מערכת בשני קצבים: מתכנן כבד שמייצר מבנה תשובה קומפקטי, ומנסח קטן שמפתח אותו לטקסט. המתכנן חוזר לפעולה רק כשנדרשת החלטה חדשה, התגלתה סתירה או שהמנסח הגיע למשהו שלא נכלל בתוכנית. הסיכון: המנסח עלול להוסיף טענות שלא היו בתוכנית, או שתכנון מדויק מספיק יהיה ארוך ויקר כמעט כמו כתיבת התשובה. ועוד דבר: זה עשוי לחסוך עבודה ואנרגיה, אבל לא בהכרח זיכרון שיא.

5. מודל קטן שמעמיק בלולאה, במקום מודל עמוק עם המון משקולות. לשמור מעט שכבות ולהפעיל אותן שוב ושוב. שאלה קלה תסתיים אחרי מעט סיבובים. שאלה קשה תקבל יותר. כך אפשר לנסות להחליף קיבולת משקולות קבועה בזמן חישוב משתנה. הסיכון ברור: אפשר לחסוך זיכרון ובו בזמן להגדיל את זמן ההרצה ואת צריכת האנרגיה.

                }
                LOG(INDENT INDENT INDENT "[");
                for (int64_t i0 = 0; i0 < ne[0]; i0++) {
                    if (i0 == n && ne[0] > 2 * n) {
                        LOG("   ..., ");
                        i0 = ne[0] - n;
                    }
                    const float v = common_ggml_get_float_value(data, type, nb, i0, i1, i2, i3);
                    LOG("%12.4f", v);
                    if (i0 < ne[0] - 1) {
                        LOG(", ");
                    }
                }
                LOG("  ],\n");
            }
            LOG(INDENT INDENT "],\n");
        }
        LOG(INDENT "]\n");
        LOG(INDENT "sum = %f\n", sum);
    }

    if (abort_on_nan) {
        if (std::isnan(sum)) {
            LOG("encountered NaN - aborting\n");
            exit(0);
        }
    }
}

7. זיכרון של מצב, לא זיכרון של כל ההיסטוריה. המודל יחזיק "איפה אנחנו עכשיו", במקום לשמר ייצוג נרחב של כל מה שנאמר. מצב של המשפט הנוכחי, מצב של השיחה, ומצב ארוך-טווח. כל שכבה מתעדכנת בתדירות אחרת. הסיכון: דחיסה יכולה למחוק בדיוק את הפרט שיישאל בהמשך.

8. לקמפל יכולת, במקום להריץ מודל כללי שוב ושוב. מודל גדול שמבין משימה, ואז לא רק עונה עליה, אלא מייצר מנגנון קטן שיוכל לטפל במשפחה של משימות דומות. לא מטמון של תשובות, מטמון של יכולות. אם יצירת המנגנון עולה C, וכל שימוש חוסך S, צריך יותר מ-C/S שימושים כדי שההשקעה תשתלם.

9. לאמן על GPU מודל שנועד בכלל לפעולות פשוטות. מותר שהאימון יהיה יקר, אבל תוצר האימון לא חייב להיראות כמו רשת רגילה במספרים בעלי דיוק גבוה. לאמן ישירות מול מחיר הפעולות של מעבד היעד.

למה לא מספיק לחלק את המודל לשכבות ולטעון אותן. נניח שאחרי כל המטמונים עדיין צריך לקרוא 9GB מהאחסון לכל טוקן, ושקצב הקריאה האפקטיבי הוא 400MB בשנייה. רק הקריאה תדרוש 22.5 שניות לטוקן. באותה הנחת רוחב פס, כדי להגיע לשלושה טוקנים בשנייה, מותר לנו לקרוא לכל היותר כ-133MB חדשים לטוקן. מכאן אני גוזר את היעד האמיתי: לא רק להקטין את הזיכרון, אלא להוריד את כמות המידע החדש שצריך להביא בכל צעד, מגיגה-בייטים לעשרות מגה-בייטים.

הרעיון: מודל מלא עם חישוב מדורג. אנחנו לוקחים checkpoint קיים. בשלב הכנה על מחשב חזק, מפרקים את החישובים שלו לשני חלקים. החלק הראשון הוא קירוב זול שנשאר ב-RAM. החלק השני הוא המידע שמשלים את הקירוב בחזרה לחישוב המקורי, שנשמר ב-SSD בחבילות שאפשר לקרוא בנפרד. למטריצת משקולות מסוימת אפשר לכתוב W = W_base + R_1 + R_2 + ... + R_n, ולכן Wx = W_base x + R_1 x + ... + R_n x. ההימור שלנו הוא שעבור קלט מסוים, חלק קטן מהתיקונים יספיק כדי לקבל תוצאה שימושית מאוד.

איך יודעים איזה תיקון חשוב, בלי לקרוא אותו. לכל חבילת תיקון תקציר מתמטי קטן שנשאר בזיכרון, מידע על גודל ההשפעה האפשרית שלה. נניח שחילקנו את מטריצת השארית לקבוצות עמודות. לכל קבוצה g אפשר לחסום את השפעת החבילה באמצעות הנורמה של R_g כפול הנורמה של x_g. את החסם על הנורמה של R_g מחשבים מראש. כלומר, לפעמים אפשר לדעת שחבילה אינה יכולה להשפיע הרבה, בלי לקרוא את המשקולות שלה.


הניסוי הראשון שהייתי עושה: לא לכתוב מנוע שלם ל-Raspberry Pi, אלא לברר אם יש בכלל מספיק חיסכון בייצוג המוצע. מודל ייחוס אחד, ללא ערבוב בין רמות דיוק. לבדוק תחילה בחירה אידאלית של תיקונים. להחליף את הבחירה האידאלית במנגנון זול. ולבסוף להריץ על ה-Pi ולמדוד את כל המערכת: זמן עד הטוקן הראשון, קצב המשך התשובה, זיכרון כולל, קריאות SSD ואנרגיה.

ההימור המרכזי שלי הוא שהפריצה לא חייבת להיות "מודל קטן שיודע פחות". היא יכולה להיות מודל בעל יכולת רחבה, שבכל רגע משלם רק על החלק הקטן מהיכולת שבאמת נחוץ עכשיו.
