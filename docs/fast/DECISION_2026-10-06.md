## 2. What the layer skip may be used for, and the evidence

Rule (full table of consumers in `docs/fast/LAYER_SKIP.md`): in Gemma 4 E2B and E4B the upper 20 and 18 layers
store no keys or values. A token without the output flag therefore reaches nothing through those layers except
things that read one row per token from them. Those readers are guarded: unmasked drafter export, exported
per-layer inputs, an eval callback, training, embedding inputs, per-sequence KV streams with several sequences
in a batch. In every guarded case the reference graph runs. With the Gemma 4 assistant the target switches to
the masked export, because that drafter shares the target's KV cache and only reads rows of output tokens.

Evidence (API-level tool `pi/fast/tests/fast_check.cpp`, built against the patched tree and against an
unpatched copy of the pinned source; nine scenarios: plain decoding, prompt chunks of 1-9 tokens, 511/512/513-token
prompts in different splits, reused context after truncation, two sequences in one batch, output flags on
non-final rows, draft-verify-rollback by hand, embeddings, batch widths 1-9):

| Pi 5, patch v7, against the unpatched build | E2B | E4B |
|---|---|---|
| All switches off: logit vectors bit-identical | 140 / 140 | 140 / 140 |
| Layer skip: logit vectors bit-identical | 137 / 140 | 137 / 140 |
| Layer skip: persistent KV state identical (digests) | 32 / 32 | 32 / 32 |
| Layer skip: argmax changes / token sequences that differ | 0 / 0 | 0 / 0 |
| Layer skip: worst KL on the three vectors that differ | 2.9e-4 | 3.6e-4 |
| Control, reference against itself, same tokens in another batch split: worst KL | 5.0e-4 | 9.3e-4 |
| Draft-verify-rollback scenario commits the plain greedy tokens | yes | yes |

The three vectors that differ are the 511-513-token prompts: with one query row left and at least 512 cache
cells, ggml's CPU flash attention takes its single-query path, which sums in another order. The reference shows
a larger difference between two ways of batching the same tokens, so this is inside the engine's own variation,
but it means "bit-identical logits" is not claimed.

Server level, greedy, one stream: the patched build produced the reference text in 115 of 115 comparisons on
2026-10-06 afternoon and in all 54 patched requests of the matched benchmark below (27 plain, 27 with the
drafter; English, Hebrew, German, code, prompts of 21-374 tokens). In the model screen (section 5) one E2B answer
of 253 tokens differed between "reference, plain" and "patched, with drafter". Nine runs of that request showed
that the unpatched build with the drafter gives the same second version, and the patched build without drafter
the first, with any combination of switches. The statement that holds is therefore **patched = reference in the
same mode**; whether a drafter reproduces plain greedy text exactly is upstream behaviour (it did in 184 of 186
answers tonight).

Scope that is supported: text input, plain decoding, chunked prompts, context reuse, several sequences in a
unified KV buffer, non-final output rows, the Gemma 4 assistant with acceptance, rejection and rollback, the
non-flash attention path and a quantized KV cache (the last two on the desktop with the upstream version).
Not tested: image and audio input (falls back), LoRA and control vectors, GPU backends.
Not applicable: 26B-A4B and 31B (no shared-KV layers; the condition is false and nothing changes).

## 4. Vocabulary shortcut of the drafter

What was built: the Gemma 4 assistant's own output layer as Google ships it. Instead of scoring all 262,144
tokens with its 256-wide vocabulary matrix (37.7 MB read per draft step), the drafter scores 2,048 cluster
centroids, keeps the 32 best clusters and scores only their 4,096 tokens (`PIGEMMA_MTP_CENTROIDS=1`, patch v6/v7).
The two tensors it needs are in Google's public QAT assistant checkpoints but are dropped by the llama.cpp
converter; `pi/fast/make_centroid_gguf.py` adds them to the drafter file. **The target model is untouched and
still verifies every token.** The idea of an approximate output head for the target itself is deferred: no
target computation is approximated anywhere in this work.

Pi 5, E2B fast profile, 50 requests (6 free prompts + the 44 held-out questions with task budgets; English 16,
Hebrew 13, German 10, code 11), 3 drafts per pass, greedy, `--reasoning off`, two alternated repetitions
(`results/pi-real/fast3/centroids/`):

| Drafter head | 50 requests, s | Decode tok/s | Draft construction, ms per pass | Target verification, ms per pass | Whole pass, ms | Drafts accepted | Committed tokens per pass | Same text as dense |
|---|---|---|---|---|---|---|---|---|
| dense (reference) | 241.6 / 241.4 | 15.71 / 15.71 | 21.1 / 21.7 | 148.1 / 147.6 | 169.3 | 2135 of 3720 = 57.4 % | 2.659 | - |
| 32 clusters (Google's setting) | 239.3 / 239.0 | 15.87 / 15.89 | 16.1 / 15.8 | 148.2 / 148.3 | 164.2 | 2110 of 3797 = 55.6 % | 2.608 | 50 of 50 |
| 64 clusters | 243.0 | 15.60 | 20.3 | 147.8 | 168.0 | 2117 of 3777 = 56.0 % | 2.622 | 50 of 50 |

| Language | Requests | Dense: decode tok/s | 32 clusters: decode tok/s | Dense: accepted | 32 clusters: accepted |
|---|---|---|---|---|---|
| English | 16 | 13.45 / 13.50 | 13.85 / 13.83 | 42.3 % | 42.0 % |
| Hebrew | 13 | 13.95 / 13.88 | 14.06 / 14.06 | 45.4 % | 43.4 % |
| German | 10 | 14.51 / 14.40 | 13.87 / 13.90 | 47.1 % | 42.0 % |
| Code | 11 | 16.97 / 16.99 | 17.21 / 17.24 | 66.4 % | 64.7 % |

- Draft construction drops by a quarter (7.1 -> 5.3 ms per drafted token). That is 5 ms of a 169 ms pass, because
  the pass is dominated by the target's verification (148 ms, unchanged).
- The restricted head proposes a slightly different token now and then, so 1.9 % fewer tokens are committed per
  pass. Net: **decode +1.1 %, whole series -1.0 %**, repeatable to the second decimal. English +2.7 %, Hebrew
  +1.0 %, code +1.4 %, German -4 % (its acceptance falls from 47 to 42 %). Per request: 17 faster by more than
  2 %, 5 slower, 28 within 2 %.
- Greedy agreement: identical output in 50 of 50 requests on the Pi (32 clusters twice, 64 clusters once) and
  in 6 of 6 on the desktop (32 clusters). Time to the first visible text is unchanged (0.39-0.40 s median).

Sampling (temperature above zero), audited on the desktop (`pi/fast/analyze_sampling.py`,
`results/desktop-fast/sampling/`):

- Default verification in llama.cpp a7b94df (`--spec-draft-sampling greedy`): the drafter proposes its most
  likely token, the target samples from its own distribution with its own random stream and the draft is kept
  while it equals that sample (`common_sampler_sample_and_accept_n`). Proposal probabilities are not used at
  all, so a different proposal can change how many tokens a pass commits but not which. Measured: at
  temperature 0.8 with fixed seeds the dense and the cluster head commit identical text in 6 of 6 long answers;
  at temperature 1.0 the output equals plain sampling with the same seed in 400 of 400 short answers, for both
  heads.
- Rejection-sampling verification (`--spec-draft-sampling probabilistic`, off by default): the drafter samples
  from its 10 best candidates at the target's temperature and the target accepts with probability min(1, p/q),
  otherwise it draws from the normalized positive part of p - q (`common_sampler_sample_and_accept_n_rejection`).
  This keeps the target's distribution for any proposal distribution q, provided the recorded q is the one the
  draft was drawn from. With the cluster head both come from the same restricted logits (tokens outside the
  4,096 candidates are masked before the sampler), so the condition holds. Measured on 400 seeds of a
  four-random-digits prompt: digit histograms against plain sampling give chi-square p-values of 0.57-1.0 for
  positions 1-3 and 0.08 for position 4, the same for both heads (their histograms differ by at most 2 counts).
  No sign of a distortion; 400 samples would not show a small one.
- Found on the way, not caused by the patch: with a drafter attached, seeded sampling of long answers is not
  the same random stream as without one (3 of 6 answers differ at temperature 0.8). The unpatched reference
  build does exactly the same, token for token.

Result: correct and cheap, but worth about 1 % on this board. It stays an optional switch and needs a
non-standard drafter file. It is not a reason to carry a patch. If llama.cpp's converter learns to keep the two
tensors, it becomes a free default.

What the screen shows:

- With enough room to answer, E2B's score is 23 of 44 (the 96-token product test of the afternoon gave 16 of 44
  because nine code answers were cut; that short-cap test stays a separate product scenario). The fast profile
  does not change the score of either model.
- **E4B with the fast profile and its assistant is both better and faster than E2B on the reference build**:
  32 against 23 correct, 273.7 against 464.9 s for the series, 10.4 against 7.4 tok/s decode. Its assistant
  works better than E2B's on these tasks (3.07 tokens per pass, 73 % of drafts accepted).
- Against E2B with the fast profile, E4B costs 36 % more time for the series (273.7 against 200.7 s), about
  1.4 s more on a short answer (median 2.12 against 0.75 s), the same time on long answers (90th percentile
  14.4 against 14.5 s, E4B writes shorter code), and 3.4 GB more memory, for 9 more correct answers.
- Neither small model can do the number tasks without thinking (2 of 10 each); the 26B does all ten.
- **The 26B is the only one that is reliably right (42 of 44)**, at 3.5 times the time of E2B's fast profile and
  2.6 times that of E4B's (699 against 201 and 274 s), with 5.6 s to the first visible text on these prompts
  and the whole memory of the board in use (see section 6 for what that did to swap).
- The 26B's assistant is accepted far more often than the small models' (84 % of drafts, 3.4-3.6 tokens per
  pass) and still gains only 35 %: decode 3.77 -> 5.08 tok/s, because a pass with four rows costs 2.6 times a

- Order effect, stated so the table is not over-read: the 26B plain run went first and paid for filling the
  page cache from the USB stick (its first twelve requests processed prompts at 1.5-9 tok/s). With the prompt
  time of the second run its series would be about 831 s instead of 929 s. Decode rates are not affected.
- Output identity inside this screen: E4B fast profile = E4B reference in 44 of 44 answers. E2B: 43 of 44; one
  253-token code answer differs in one comment near its end (both versions pass the tests). The cause was isolated with nine runs of that one request (`results/pi-real/fast3/attrib/`): the **unpatched reference build with the drafter** already produces the second version; the patched build without drafter produces the first with no switch and with all switches; the patched build with drafter produces the second with no switch, with each switch alone and with all three, always with the same 171 accepted drafts. So the difference comes from upstream's batched verification (a pass with several rows rounds differently from a pass with one row, and a near-tie flipped at token 240), not from any patch. The claim that holds is therefore: **patched = reference in the same mode** (plain against plain, drafter against drafter). "Drafter = plain" is a property of llama.cpp that holds almost always (184 of 186 answers in the matched benchmark and this screen; the other exception is one 26B code answer), not a guarantee.

## 6. 26B prepacking: go or no-go

"Prepacking" = storing the weights in the 4-row interleaved layout that llama.cpp's fast kernels use. llama.cpp
does this at load time in anonymous memory; on this board that does not fit for the 26B (it went to swap in the
morning), so the 26B runs with `-nr` (weights stay in their file mapping, row-by-row kernels). The hypothesis to
test was "packing lifts the 26B from 4.6 to 6.5 tok/s".

What the 26B reads per pass (modeled from the tensor sizes in the file, `results/pi-real/26b_bytes_per_token.json`):

| Part | Bytes | Read per pass |
|---|---|---|
| attention projections (Q4_0) | 625 MB | all, once per pass |
| output matrix (Q6_K) | 606 MB | all, once per pass |
| dense feed-forward (Q4_0) | 301 MB | all, once per pass |
| expert router (F32) | 44 MB | all, once per pass |
| experts, 128 per layer (Q4_0) | 12,846 MB | 8 of 128 per layer **per token row**: 803 MB per row |

One row: 2.38 GB. At the board's 12 GB/s that is 198 ms, i.e. **5.0 tok/s is the ceiling of plain decoding
whatever the layout**. Four rows on different experts: 4.79 GB = 399 ms.

Measured on the 44-task screen (steady state, `-nr`): one-row pass 267 ms median (3.77 tok/s); a draft-verify
cycle with the assistant 686 ms median for 3.4-3.6 committed tokens (5.08 tok/s; 5.16 on the long answers).

| Question | Evidence | Answer |
|---|---|---|
| Does packing help plain decoding? | Dense parts of a one-row pass already run at 10.4-11.4 GB/s unpacked (26B profile, decode phase: attention 58.6 ms, output matrix 53.0 ms, dense feed-forward 29.1 ms). E2B, same board: one-row pass 129 ms packed against 143 ms unpacked. Packed expert kernels inside the real 26B (CF-Engine Milestone A, bit-identical): 4.61 -> 4.63 tok/s | **No.** At most about +5 % |
| Can 4.6 -> 6.5 tok/s come from plain decoding at all? | 6.5 tok/s would need 1.85 GB per pass; the model reads 2.38 GB | **No**, above the memory ceiling of 5.0 |
| Does packing the experts help a verification pass? | Each row routes to its own experts: 803 MB more traffic per row whatever the layout (67 ms at memory speed). A cycle costs about 140 ms per extra row; half of it is this traffic | **No.** And 12.8 GB of packed experts fit nowhere |
| Does packing the dense part help a verification pass? | Representative operations, E2B on this board, 4 rows per pass, same kernels and quantization types as the 26B's dense part: **110.8 ms packed against 255.4 ms unpacked** for 1.03 GB of layer weights (`results/pi-real/fast3/profile26/`). Unpacked, four rows cost 2.3 times one row; packed, 1.13 times | **Yes, on paper**: about 170 ms of the 686 ms cycle |

Projection, labelled as such: with the dense 1.58 GB packed and everything else unchanged, a cycle would cost
about 170 ms less, about 500-520 ms instead of 664 ms (series mean; 686 ms median on the long answers):
**5.1 -> about 6.5-6.8 tok/s with the assistant (+28 to +34 %)**. It rests on E2B ratios applied to the 26B's
dense tensors; nothing of it is measured on the 26B. The ceiling with every draft accepted is about 8 tok/s,
because expert traffic grows with every row. Without the assistant the same change gives about 3.8 -> 4.0.

So the hypothesis survives only in a narrower form: not "prepack the 26B", but "pack its dense 11 % and use the
assistant". The assistant alone, with no new code, already gives most of the way (3.77 -> 5.08 tok/s, same score,
same text in 43 of 44 answers; on answers of one to four tokens it is slower, 5.0-5.3 -> 3.2-4.6 tok/s, a
difference of under a second).

Costs that a prototype has to show before anyone builds more:

- **Memory.** The board is at its limit with this model: during the screen 1.3 GB of the server's own memory sat
  in swap and about 0.7 GB was still in swap afterwards; ContextFriend services stayed active and nothing
  throttled. A cold start read 3.2-3.4 GB from the stick per request. Packing the dense
  part in anonymous memory adds 1.58 GB that cannot be evicted while the original 1.58 GB of mapped pages go
  cold. A packed file avoids the copy but needs the loader work of CF-Engine's packed format.
- **Packing cost and identity.** Offline on the desktop: minutes. CF-Engine's identity check of the source file
  cost 84 s per start in Milestone A and would need a cached hash.
- **Duplicated mappings.** None if the packed tensors replace the originals in the file; 1.58 GB if both stay.
- **Verification passes.** The gain exists only for passes with 2-4 rows; with the padded-tail change they are
  handled in one sweep, without it 2 and 3 rows would lose it again.
- **Expert traffic** is untouched and sets the ceiling above.

**Decision: no-go for prepacking the 26B as a whole and for prepacking as a plain-decode measure. Go for one
bounded prototype only: selective packing of the dense tensors (attention, dense feed-forward, router, output
matrix) with the assistant attached, accepted if it shows at least +20 % committed decode throughput on the
44-task screen with identical greedy output in the same mode and no more swap than today.** The layer skip is not
part of this: the 26B has no shared-KV layers.

## 8. Decision and next component

**1. Durable commit and reproduction.** Done: local branch `fast-profile`, patch v7 against llama.cpp a7b94df,
build and test scripts, raw results with checksums, work area on the stick instead of `/tmp`, a from-scratch
build of v7 in a new directory that reproduces the correctness numbers (section 1). Nothing is pushed. The
`/goal` hook with the 100 tok/s condition is still armed and can only be cleared by the operator.

**2. Supported scope and correctness.** The layer skip is safe for Gemma 4 text models with shared-KV layers
(E2B, E4B) in plain decoding, chunked prompts, reused contexts, several sequences in a unified KV buffer and
with the Gemma 4 assistant; it switches itself off in every case where something reads one row per token from
the skipped layers. Persistent state is bit-identical; logits differ only on prompts of 511 tokens and more and
by less than the reference differs from itself between two batch splits (section 2, `docs/fast/LAYER_SKIP.md`).
Patched = reference in the same mode in every greedy comparison made.

**6. 26B prepacking: no-go, with one exception.** No-go for packing the whole model and for packing as a
plain-decode measure (5.0 tok/s is the memory ceiling of a one-row pass; packed expert kernels gave nothing).
Go for one bounded prototype: pack only the dense 1.58 GB and use the assistant, projected 5.1 -> about 6.5-6.8
tok/s, to be accepted at +20 % on the 44-task screen with identical output in the same mode and no more swap
than today (section 6). Using the assistant on the 26B needs no code and already gives 3.77 -> 5.08 tok/s.

**7. Next justified CF-Engine component.** Exactly that prototype: selective packing of the 26B's dense tensors
for multi-row verification passes. It is the only remaining item with a measured basis for a double-digit gain,
and it only matters if the 26B is the model that ships. Measured and closed, so not candidates: kernels and
assembly (Milestone A, no gain), packing the experts (traffic per row), the drafter's vocabulary head (+1 %),
longer or gated drafts (section 3b, no gain and less stable output), plain-decode packing (at most +5 %).
Not started and not proposed for the next iteration: a runtime rewrite, assembly autotuning, any approximation
of the target model. If the 26B is not the shipping model, the better use of the next iteration is to get the
layer skip accepted upstream (section 7), which removes the need to carry a patch at all.
